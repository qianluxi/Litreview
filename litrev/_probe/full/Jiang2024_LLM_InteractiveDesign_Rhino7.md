# Jiang2024_LLM_InteractiveDesign_Rhino7

- 抽取范围：全文 p.1–8（正文见 p.2–8；p.1 为网络首发封面页，p.8 后半为参考文献）

## 1. 一句话主张
- 论断：提出 LLM 驱动的设计交互新范式——由 LLM 直接按用户的自然语言指令编写程序脚本、调用 API 完成设计任务，作为传统靠键鼠操作逐步驱动各 API 运行的替代方案。
- 引文："因此，本研究针对建筑设计场景提出LLM 驱动的设计交互新范式。让LLM 直接根据用户的自然语言指令编写程序脚本调用API 完成设计任务，作为传统通过键鼠操作逐步驱动各API 运行的替代方案。" (Jiang, 2024, p.4)

## 2. 问题域
- 论断：面向专业建筑设计软件使用门槛与学习成本不断增高、建筑师与软件交互越来越复杂的问题。
- 引文："随着建筑专业知识越来越丰富和复杂，建筑设计软件的使用门槛和学习成本在逐渐增高，建筑师与软件的交互也越来越复杂。" (Jiang, 2024, p.3)

## 3. 案例或数据的表示形式
- 论断：数据以 API 摘要信息的形式组织——爬取 Rhino 官方文档网页的 HTML 源码并用正则匹配提取 RhinoScriptSyntax 模块所有 API 的摘要信息；Grasshopper/Ladybug 插件节点则封装为 API 并以相同方法获得摘要，部分节点摘要做了适当简化。
- 引文："首先采用Beautiful Soup 爬虫库爬取Rhino 的官方文档；具体的，先自动下载文档所在网页的HTML 源码文件，该文件结构化地记录了网页上的所有内容，通过正则匹配提取出RhinoScriptSyntax 模块所有API 的摘要信息。另一方面，将Grasshopper/Ladybug 插件的节点封装为API 并用相同的方法从文档中获得API 摘要信息，由于部分节点源代码过于复杂且摘要信息过长，对其做了适当简化。" (Jiang, 2024, p.6)

## 4. 相似性或检索机制
- 论断：相似性用词嵌入向量的夹角余弦度量——以词嵌入模型（如 M3E）把任务指令与 API 摘要分别转换为词嵌入向量，计算语义相似度（即向量空间中两个向量夹角的余弦），再按相似度排序取最高的若干个 API。
- 引文："具体的，首先利用词嵌入模型(如M3E)将任务指令转换为词嵌入向量(Word Embedding Vector)；然后将所有API 的摘要信息也转换为词嵌入向量，API 摘要见表1，通常只需转换API 名称、功能和输入部分；接着计算语义相似度，它是向量空间中两个词嵌入向量夹角的余弦，相似度越高，两词嵌入向量所对应的文本在语义上越接近；最后将计算出的相似度排序并选取相似度最高的若干个API。" (Jiang, 2024, p.5)

## 5. 系统形态
- 论断：形态为在 Rhino7 建筑设计软件上以表 2 的 12 类任务检验技术路线各关键环节能否被有效执行的验证性实现，据此验证该范式在建筑设计场景落地的可能性。
- 引文："为了验证LLM 驱动的交互式设计范式在建筑设计场景落地的可能性，本研究基于Rhino7 建筑设计软件见表2 共12 类任务，以验证技术路线中各关键环节是否可以被有效执行。" (Jiang, 2024, p.6)

## 6. 评价方式
- 论断：以召回率评价 API 搜索——为表 2 各类任务分别设计两条不同的自然语言指令，用 M3E 模型按该技术方案搜索与任务指令文本相似度最高的 10 个 API，结果显示任务相关 API 的召回率达到 81%。
- 引文："然后为表2 中的各类任务分别设计两条不同的自然语言指令，利用M3E 模型按照2.1 节所介绍的技术方案搜索与任务指令文本相似度最高的10 个API；搜索结果显示，召回率——任务相关API 在搜索到的API 中的比率达到了81%。" (Jiang, 2024, p.6)

## 7. 明确写出的局限
- 论断：作者承认当任务指令过于冗长时该新范式的交互效率优势不明显，因此未来的建筑设计软件宜保留传统交互方式。
- 引文："但仍需注意到，对于任务指令会过于冗长的情况，该新范式的交互效率优势不明显；因此未来的建筑设计软件宜保留传统交互方式。" (Jiang, 2024, p.8)
