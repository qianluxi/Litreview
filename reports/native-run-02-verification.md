## 三、机制缺陷：3/8 次审计派发返回「成功的空壳」

报告写的是「B1 首次 result 为空；恢复同一会话后补交 16 行」。库里的实际记录：

```
14:18:29  T1 C4审计 B1   out=98 字符  status=completed
   <task id="ses_e410ab205ffeOCHyRo3WApZ0F5" state="completed">
   <task_result>

   </task_result>
   </task>
14:29:53  T4 剩余审计 B3  out=98 字符  status=completed
14:29:53  T4 剩余审计 B5  out=98 字符  status=completed
```

**8 次审计派发里 3 次（37.5%）返回 `state="completed"` 但 `<task_result>` 是空的。** 而子会话里其实有完整内容（B1 会话产出 1284 字符的 16 行表）。

补救方式报告写对了：带 `task_id` 再派一次，子会话被 resume，重新输出结论。取证确认 `in=['description','prompt','subagent_type','task_id']`，output 变 1382 字符。

### 为什么这是本轮最该记住的一条

它和上一轮 PDF 那条是**同一个模式**：

| | 上一轮 | 本轮 |
|---|---|---|
| 工具 | `read` | `task` |
| 状态 | `completed` | `completed` |
| 声称 | `"PDF read successfully"` | `<task_result></task_result>` |
| 实际 | `metadata.loaded = []`（0 页） | 空字符串 |
| 危险 | 拿着空内容往下编 | 静默丢掉整批判定 |

两次都是**工具层不报错**。这次没出事，是因为 orchestrator 主动检查了返回内容长度并补派——是人的自觉，不是机制。

**建议**：任何 `task` 返回都要检查 `<task_result>` 是否为空，空则带 `task_id` 重派。这条应写进 runbook，不是写进某个 agent 的提示词。

## 四、方法论问题：48 条片段里 14 条的根源不在论断层

这是本轮最实质的发现，报告完全没有触及。

### 4.1 扩句 7 条，只有 3 条真正达标

按 `AUDIT_CONTRACT.md` 的实质标准（单看这一句能否读懂在说谁）逐条判：

| id | 扩句后起首 | 判定 | 理由 |
|---|---|---|---|
| B2-09 | `Finally, we reviewed and collected data from 14 design projects.` | **SELF** | 完整句，主语明确 |
| B3-02 | `Furthermore, a weak point of our approach is that it is only able...` | **SELF** | 主语 `a weak point of our approach`，指向清楚 |
| B3-16 | `Floor plans are digitally represented in various ways...` | **SELF** | 完整句，最好的这一条 |
| B2-01 | `These reference drawings are used to guide solutions...` | **DEPENDENT** | `These` 指向前文的哪批图纸，单看不知 |
| B2-05 | `To focus on..., this section introduces the construction...` | **DEPENDENT** | `this section` 指向当前节，脱上下文不知是哪节 |
| B2-08 | `and the primary object-based representation uses...` | **不合格** | 以 `and` 起首，不是句子起点 |
| B3-03 | `eac h ob ject circle or ellipse will b e represen ted b y...` | **不可用** | 266 字符，无标点，断词连篇 |

**只有 3/7 真正解决。** 报告 §5 诚实写了「未对扩句后的 7 条重跑 auditor」，所以它没声称 7 条都转 SELF——但没有指出这 4 条需要返工。

### 4.2 契约有个漏洞：`These X` / `this X` 不算依赖

`AUDIT_CONTRACT.md` 第五节写的是「只有主语缺失或**代词作主语**（`it/this/these/such` + 谓语）才判 `DEPENDENT`」。而 `These reference drawings are...` 的主语是名词短语 `reference drawings`，`these` 只是限定词——按字面规则判 **SELF**，按「单看能否读懂」判 **DEPENDENT**。

这不是审计员判错，是口径没覆盖。建议补一条：

> 指示代词作**限定词**（`these drawings`、`this section`、`such approaches`）时，若指代对象未在引文中出现，同样判 `DEPENDENT`。判据是「把引文单独贴到综述里，读者是否需要往回翻」。

### 4.3 `Borner1993` 根本不该被扩句

扩出 266 字符的断词长串不是 agent 偷懒。查 PDF 文字层：

```
Borner1993  p.5：429 行 / 437 词 = 1.02 词/行，短行占比 100%
  原文长这样：b e / tac kled / prop erly / co v er / giv en
```

**这篇 PDF 的文字层是逐词换行的**（排版把每个词单独成行），任何按行取句的抽取都必然得到碎片。`verify` 之所以全过，是因为它把空白全删了再比对。

全量扫描 22 篇的文字层：

| 文献 | 词/行 | 短行占比 | 48 条片段中的贡献 |
|---|---:|---:|---:|
| Borner1993 | **1.03** | 100% | **7 条** |
| Zhang2006 | **2.93** | 70% | **7 条** |
| Maher1987 | 3.43 | 68% | 0 |
| 其余 18 篇 | 4.86–11.73 | ≤40% | 34 条 |

**48 条片段里的 14 条（29%）来自这两篇。** 它们的引文不是「笔记写得截断」，而是「源文件文字层碎，抽取时按行取就必然是碎片」。

后果很直接：把这 14 条交给 auditor 判 `DEPENDENT`、再让 extractor 扩句，方向就是错的——扩句只会把碎串变得更长。B3-03 已经证明了：10 词的碎串扩成 266 字符的碎串。

**建议**：

1. `Borner1993`、`Zhang2006` 两篇的引文**不走 `texts/*.txt`**，改人工按 PDF 视觉抄录，或先用版面重建（PyMuPDF 的 `get_text("blocks")` 按块而不是按行）重抽。
2. `litrev.py index` 之后应输出一张「文字层健康度」表（词/行、短行占比），低于阈值的文献在抽取前就标红，不要等 C4 才发现。
3. 在问题解决前，这两篇的 14 条判定结果只能当「已知有问题」记录，不能当「已处理」。

## 五、判定质量抽检：88 条 SUPPORTED 里有通融

| B2-16 | 相似度用 χ2 距离计算 | `...Their similarity is calculated by means of the χ2 distance:` | SUPPORTED | 判定正确 |

**6 条里 3 条偏宽（50%）。** 样本太小，不足以给出总体比例，但方向与两条已知证据一致：

- v1 变异测试：该判 `UNSUPPORTED` 的有 2/5 被判成 `PARTIAL`（严重度偏轻）
- 本轮 131 条里 `UNSUPPORTED` 只占 1 条（0.8%），而 `PARTIAL` 占 32%

**结论不变，但要收紧**：`SUPPORTED` 可以自动放行这个说法，在 n=6 里已经有 50% 的反例，**不能再这么说**。正确的用法是：

## 七、顺带修了取证工具的两处误判

### 7.1 `--since` 把根会话排除，然后断言「没派发过」

第一次跑：

```
[2] 根会话 0 个 / 子会话 13 个
[4] [NO] 本项目会话里没有 task 工具调用
    → 原生 Subagent 派发尚未发生
```

而实际上根会话里有 17 次 task。原因：本轮是在**上午那个根会话里继续**（`time_created` 10:10），`--since 2h` 把它过滤掉了，而 task 记录全在根会话的 part 里。子会话是下午创建的，反而留下来了。

这和上一轮 `project_id='global'` 那次是同一个错误形状：**过滤器把有证据的对象排除，然后断言证据不存在**。

已修：按「窗口内的会话 + 它们的全部祖先」取闭包，再把 part 裁到窗口内；报告里明确打印「根会话 X 创建于 10:10，早于 --since，因窗口内有子会话而纳入」。

### 7.2 续派的任务被错配到另一个会话

「T1 B1 重取判定表」指向了 B3 的会话——因为原逻辑按「父会话 + agent + 创建时间最近」匹配，14:22:04 那个时点，B3 会话比 B1 会话只近 1 秒。

已修：优先采信 task output 里的 `<task id="ses_...">`（续派时只有它指得回原会话），时间邻近降为最后的兜底。修后第 4 条正确指向 `ses_e410ab205ffeOCHyRo3WApZ0F5`。

`--selftest` 5/5 通过。

## 八、结论与下一步

**技术层全部通过**：131/131 判定齐全且自洽、131/131 依据可回溯、批次切分无重复、7 条扩句在标注页逐字存在、0 越界、17 次派发全部可定位到子会话。

**但「C4 补齐」只完成了一半**，原因有三个，按紧急程度：

1. **14 条引文的根源在语料层，不在论断层**（Borner 7 + Zhang 7）。扩句无效，要换抽取方式或弃用。这是唯一会污染成稿的硬问题。
2. **4 条扩句要返工**：B2-01、B2-05（指示代词依赖）、B2-08（`and` 起首）、B3-03（不可用）。同时给契约补一条「指示代词作限定词也算依赖」。
3. **88 条 SUPPORTED 需要抽检**，n=6 里已见 3 条偏宽。不要按「已通过」处理。

**T5 未做**（`permission` 未启用），frontmatter 只有两项，已确认。

一句话：**这轮把「不知道哪条有问题」变成了「知道 43 条有明确问题、14 条有问题但根源在别处、88 条里大约还有一成没查出来」。这就是分诊单该有的样子，但它不是合格证。**
