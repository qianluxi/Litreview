## 四、三处需要修正的表述

### 4.1 PDF 直读：结论对，但归因错了（重要）

报告 §1.2 写的是「extractor 用了 `read`，返回：

```
PDF read successfully
ERROR: Cannot read pdf (this model does not support pdf input). Inform the user.
```
」

**库里的实际工具状态不是这样。** T0 那次 `read` 的 part 原文：

```
tool     = read
status   = completed
output   = "PDF read successfully"
metadata = {"preview": "PDF read successfully", "truncated": false, "loaded": []}
```

也就是说：**工具报告成功，状态是 completed，但 `loaded` 是空数组**——5 页的 PDF 一页都没被加载进上下文。那句报错只出现在模型侧收到的附件里，模型自己的推理原文正好记了这一层：

> The read tool returned "PDF read successfully" but the attached media says ERROR: Cannot read pdf (this model does not support pdf input).

差别为什么重要：

- 按报告的写法，读者会以为**工具报错**，于是判断「这是模型不支持 PDF 输入」，换模型即可。
- 按库里的实情，是**工具自称成功、实际交付 0 页**。任何只看 `status == completed` 就往下走的编排逻辑，都会在这里踩空——它不会报错，它会拿着空内容继续编。

建议改为：

> `read` 返回 `status=completed`、`output="PDF read successfully"`，但 `metadata.loaded=[]`（0 页加载）。真正的错误由模型侧附件给出：`Cannot read pdf (this model does not support pdf input)`。**工具链层面不报错**，这是本次最该记住的一条。

顺带一个正面结论：全轮**只有 T0 试过 1 次 PDF**，失败后再无任何会话重试，没有人自作主张去试 OCR 或转格式。HANDOFF 的失败处理被人（orchestrator）守住了。

## 五、报告没写、但更该知道的三件事

### 5.1 文件归属是机制上干净的，不只是嘴上说的

23 个 extractor 会话，**每个只写了 1 个文件**，无一例外：

```
write 调用 23 次 / edit 调用 15 次，分布在 23 个会话
每个会话的唯一落点 = 自己那一篇的 md
```

本轮没有启用 `permission` 块，所以这不是权限拦出来的，是**行为层**的干净。区别要说清：这证明「这次没人越界」，不证明「下次越不了界」。

### 5.2 信息隔离同样干净，且只有一次越界苗头

- 21 个抽取会话读 `_probe/texts/`，**每个只读了 1 个 txt，0 个会话读过 2 篇**。
- 全轮只有 1 次读 PDF（T0），此后无人重试。
- **没有任何 extractor 读过 `litrev.py`、`_index/`、或别人的稿子。** 这是上一轮在 WorkBuddy 里出现过的问题（agent 读裁判源码模仿判定逻辑），本轮没有复现。
- 唯一一次读 `litrev.py` 的是 `checker`（1 次）。它是裁判方，读工具源码不构成「生产方照着答案写」，风险等级低——但如果要加 `permission`，这条正好是第一个该堵的口子。

### 5.3 131 条里的 36.6% 是句中片段 —— 这是 C4 的真实风险量级

报告说「131 条未做 C4 审计」，读起来像是一件待办。实际量一下：

```
full 131 条中，按形式判据（首字母小写 或 未以句末标点结尾）为句中片段：48 条 = 36.6%
```

例：`to guide solutions for similar architectural situations.`、`it is only able to ﬁnd the physical existent rooms.`、`a given problem by finding matches between`。

这些 `verify` 全 PASS（逐字存在、页码对），但自足轴大概率判 `DEPENDENT`，支撑轴也可能因缺主语而判 `PARTIAL`。48 条是**风险上界**不是判定结果，但它把「待办」翻译成了一个可估的量：**至少三分之一的全量引文，写进综述前需要扩句或改转述。** 这比再抽 20 篇更紧急。

## 七、顺带修了取证工具的一个缺陷

第一次跑取证时，工具在 `[1] 项目是否被客户端识别` 里输出：

```
[NO] 库中没有该路径的 project 记录
     → 该目录从未在 OpenCode 客户端里打开过，或打开后没有产生任何会话
```

**这是误判。** 原因：该会话的 `project_id` 是 `'global'`，路径只落在 `session.directory` 上；而脚本的 `[1]` 只看 `project` 表按 `worktree` 匹配。会话检索本身有 `directory` 兜底（所以会话树能正常列出），只有这一行显示没兜底，于是「跑过一轮」被显示成「从未打开过」——正好是这个项目最忌讳的那种错误结论。

已修：匹配不到 project 但能匹配到会话时，改报 `[PARTIAL]` 并列出 `project_id` 与 `directory`，不再断言「从未打开过」。`--selftest` 5/5 通过。
