## 二、报告 §二 有一处事实错误：权限拒绝不是 0 次，是 5 次

报告写「三次都没有权限拒绝」，数据库里明确有 **5 条 `status=error` 的 `read`**，全部是审计员想读**自己刚写的输出文件**：

```
auditor-frag-b1  read  out_B1.md   ×1   "The user has specified a rule which prevents you from using this specific tool call..."
auditor-frag-b2  read  out_B2.md   ×2
auditor-frag-b3  read  out_B3.md   ×2
```

错误原文带完整 ruleset，是权限硬隔离生效，不是越权成功。

**根因**：生成器给 `auditor-<批次>` 的 `read` 只列了「契约 + 本批输入」，没列本批输出。`edit` 允许写 `out_B{n}.md`，但 `read` 不允许读回来——**审计员写完无法自查**。B2 因此把同一份 1251 字符内容原样写了两遍（两次 `write` 的 content 逐字相同，中间夹着一次被拒的 `read`）。

**影响**：不影响交付正确性（最终文件格式全对，且主控按 HANDOFF-04 §验收 逐批以文件为准兜住了），但报告的事实陈述错误，且暴露一处真实设计缺口。

**未修，需决策**：在 `tools/gen_subagents.py` 里给 auditor 的 `read` 加 `(BATCH_OUT, "allow")` 即可。这不破坏闭卷（仍读不到别的批次），但要重新生成 9 个 `auditor-*`，下一轮得重启 OpenCode。本轮核验不擅自引入需要重启的变更。

## 三、报告 §六 的核心结论归因不纯：「14.3% 漂移」是上界，不是测得的误差

报告说「28 条输入文字一字未变的条目重判，4 条判定码变了 ⇒ 闭卷判定不一致率 4/28 ≈ 14.3%」。

**前半句我验证过，是真的**：取 `out_B1/B2` 最后改动的提交 `147f8e4`、`out_B3` 的 `e8c140b`，解析当时的 `FRAG_B*.md`，与当前批次输入逐条比对（论断 + 引文）——**28 条逐字相同，20 条变过，变动清单与 `HANDOFF-04` 列的 20 条完全一致**。两套独立算法互证，报告这里没算错。

**但漏了一个变量：契约版本变了。**

| 判定时点 | 契约版本 | 行数 | 有无 §七 v1.1 |
|---|---|---:|---|
| B1 / B2 旧判定（`147f8e4`） | 11-09 上午 | 69 | **无** |
| B3 旧判定（`e8c140b`） | 11-09 晚 | 76 | 有 |
| 本轮重判（当前 `609172e`） | 11-10 09:22 | 90 | 有 + §四格式要求 + §五.3 消歧义 |

§七.1「指示代词作限定词也算依赖」是**新增的判定口径**（变严方向），§七.2 是抽检纪律。所以：

- B1-07、B1-08、B2-14 这 3 条属于「输入未变，但**规则版本不同**」，不能算随机漂移。其中 B1-08 `SELF → DEPENDENT` 正是自足轴口径敏感的方向。
- 只有 **B3-10** 是同契约版本（e8c140b → 当前，仅格式/消歧义）下的重判，1/16 ≈ 6.3%。而它 `DEPENDENT → SELF`，引文里 `These problems are often ill-` 是代词作主语，按契约 §五.1 应判 `DEPENDENT`——**新判反而可疑，更像判错而非漂移**。
- 报告据此推出的「旧表偏松」「R1–R5 漂移率可能同阶」也因此证据不足。

**准确说法**：同一份输入在**规则版本改变**的条件下重判，48 条里 18 条判定码变化；其中输入与规则都未变的那部分，观察到 1 条变化但要单独复核。要真测一致性，应在**固定契约**下对 REST 五批做双跑（另存对照文件、不覆盖旧表），而不是拿「跨版本重审」当双跑。

报告 §六 建议的「闭卷判定双人/双跑一致性检验」方向是对的，只是本轮数据还撑不起 14.3% 这个数。

- **0 次 `checker` 派发**：本轮主控自己跑了 22 次 bash，含开工自检 5 条与收尾 `audit-count`/`audit-stale`。这是 `HANDOFF-04` 明确授权的，不算违规；但「生成方与裁判同一只手」在本轮是实质状态，报告 §七.4 自己指出了这处规程张力，结论成立。
